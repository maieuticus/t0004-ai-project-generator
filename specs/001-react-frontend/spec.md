## Clarifications

### Session 2026-11-05

- Q: Soll das React-Frontend auch ohne `typescript@0.1.0` installierbar sein, oder muss dieses Modul vorher installiert sein? → A: React ist unabhängig installierbar; das vorhandene TypeScript-Modul ist keine Voraussetzung.
- Q: Welche öffentliche Kennung soll das feste Modul erhalten? → A: `react@0.1.0`.
- Q: Welche Frontend-Toolchain soll für den Vorschlag verwendet werden? → A: TSX, Node 24, React/ReactDOM und Vite; konkrete Versionen werden vor der Starter-Implementierung gepinnt und geprüft.
- Q: Wie soll die Browserinteraktion abgenommen werden? → A: Automatisierte Installations-, Typecheck-, Build- und Startertests plus manuelle Browserinteraktion bei Review-Gate 1; keine Browserautomatisierung.
- Q: Darf React neben bestehender Docker-/PostgreSQL-Infrastruktur installiert werden? → A: Ja, React darf mit bestehenden Projektionen koexistieren, erhält aber keinen Docker-Service; bestehende Docker-Voraussetzungen bleiben unverändert.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Start a React Example (Priority: P1)

A developer creating or extending a project selects the optional React frontend,
follows the project instructions, starts a local preview, and sees a working example
in a browser.

**Why this priority**: A browser-visible frontend is the central user benefit and
provides the first independently reviewable increment.

**Independent Test**: In a fresh supported project, enable the React frontend, follow
its documented local-start instructions, and verify that the example loads and responds
to a user interaction.

**Acceptance Scenarios**:

1. **Given** a fresh supported project, **When** the developer explicitly selects and
   confirms the frontend setup, **Then** the project contains the documented starter
   and can be previewed in a browser using the documented local steps.
2. **Given** the example is open in a browser, **When** the developer performs its
   primary interaction, **Then** a visible part of the example responds.
3. **Given** the developer follows the setup and preview instructions, **When** they
   do not have Docker installed, **Then** they can still start and inspect the example.

### User Story 2 - Add the Frontend to an Existing Project (Priority: P2)

A developer adds the optional frontend to a project that already has supported
language modules or infrastructure and can keep using those existing capabilities.

**Why this priority**: The generator's value depends on safe, composable additions
to existing projects, not only fresh-project output.

**Independent Test**: Add the frontend to representative existing module combinations;
verify that existing files and checks remain intact, then verify no-op and restore
behavior.

**Acceptance Scenarios**:

1. **Given** an existing supported project, **When** the developer plans and confirms
   the frontend addition, **Then** existing module and infrastructure files are
   preserved and the frontend is added without an unrelated change.
2. **Given** the frontend is installed and unchanged, **When** the developer plans it
   again, **Then** the result reports no changes.
3. **Given** a reserved frontend file was independently changed, **When** the developer
   plans or restores the frontend, **Then** the generator reports a conflict rather
   than overwriting that change.

### User Story 3 - Verify Compatibility (Priority: P3)

A project maintainer can verify that the new frontend state works with the existing
generator checks and does not change established generated states.

**Why this priority**: Compatibility evidence is required before the extension can be
accepted without regression risk.

**Independent Test**: Run focused generator tests and supported CI jobs for the new
frontend state and compare the previously supported generated states with their
established expected results.

**Acceptance Scenarios**:

1. **Given** a change to the frontend projection, **When** the supported CI checks
   run, **Then** frontend checks and existing generator checks report failures
   explicitly.
2. **Given** any previously supported language-module combination, **When** its
   projection is generated, **Then** its established generated bytes remain unchanged.

### Edge Cases

- A stale plan or a changed prerequisite is rejected before any project write.
- A foreign file at a reserved frontend path is reported as a conflict and is not
  overwritten, even if its contents appear equivalent.
- A failed local dependency installation, build, or preview is surfaced by the
  relevant project check or documented command; planning and applying do not run it.
- The frontend can be previewed without Docker; Docker and Compose integration are
  explicitly outside this feature.
- A project without `typescript@0.1.0` can still install the React frontend.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The generator MUST expose the React frontend as an explicitly selected,
  optional addition to a supported project.
- **FR-002**: The React frontend MUST produce a browser-visible example with at least
  one user interaction that produces a visible response.
- **FR-003**: The project MUST document how a developer can install required local
  dependencies and start and stop a browser preview without Docker.
- **FR-004**: A developer MUST be able to add the frontend to a supported existing
  project without removing or silently changing its existing modules, infrastructure,
  checks, or user files.
- **FR-005**: The generator MUST offer the frontend as a distinct optional addition,
  separate from the existing TypeScript console starter.
- **FR-006**: The generator MUST show planned changes before applying them, require
  explicit confirmation, and allow generated changes to be safely undone without
  overwriting independent user edits.
- **FR-007**: An unchanged installed frontend MUST produce a no-op. Missing or changed
  managed files, stale plans, or incompatible metadata MUST produce explicit conflicts.
- **FR-008**: Adding the frontend MUST NOT alter the existing console starter or
  previously supported generated project behavior.
- **FR-009**: The frontend MUST be included in the existing project validation flow,
  with failures clearly identified and without starting the application during setup.
- **FR-010**: Dockerfiles, Compose services, container builds, and Docker-based
  preview MUST remain outside this feature.
- **FR-011**: The React frontend MUST be installable without `typescript@0.1.0`;
  adding it MUST NOT change that module's files or established projection.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A developer can follow the documented steps in a fresh supported
  project and load the example in a browser without Docker.
- **SC-002**: At least one documented interaction produces an observable change in
  the example.
- **SC-003**: For each supported existing-project combination, adding the frontend
  leaves established language starter behavior unchanged and preserves unrelated
  project files.
- **SC-004**: After a successful installation, a repeated plan reports no operations;
  a stale plan or independent edit to a managed path is rejected before overwriting
  project data.
- **SC-005**: Undoing the frontend addition returns its generated files to their
  prior state and leaves unrelated user data untouched.
- **SC-006**: The focused frontend checks and the applicable existing CI checks pass
  on the project's supported CI platforms.
- **SC-007**: Planning and applying the frontend require no Docker installation and
  start no containers.

## Assumptions

- The primary user is a developer using the generator to create or extend a project.
- The first frontend increment is a local example and preview, not production
  hosting, authentication, a backend service, or a Docker deployment.
- The approved architecture treats React as an optional separate frontend addition,
  preserves the existing TypeScript console starter, and defers Docker.
- The React frontend is installable without `typescript@0.1.0`; its own
  implementation may use TypeScript without enabling the existing console module.
- React may coexist with an existing Docker/PostgreSQL projection, but it does not
  add a Docker service and does not change the existing console-module prerequisite.
- Exact toolchain versions, dependency versions, file layout, and test implementation
  are technical-plan decisions unless they change the approved user-visible scope.
