# t0004-ai-project-generator Constitution

## Core Principles

### I. Reuse the Existing Generator Engine
Generator features that change target projects MUST use the existing planning and
transaction engine, including Format 4 for supported multi-file operations. A second
write engine or general plugin framework MUST NOT be introduced without an explicitly
approved architecture decision. New fixed modules and infrastructure extensions MUST
follow the existing registration and projection patterns.

### II. Keep Architecture Simple and Deterministic
Implementations MUST prefer the smallest maintainable design that satisfies approved
requirements. Generated files, metadata, plans, and supported state projections MUST
be deterministic. Dependencies and abstractions MUST be limited to those needed by
the approved feature; alternatives and material trade-offs belong in the plan.

### III. Preserve Historical States
Existing generated bytes, module states, CI projections, snapshots, and restore
semantics MUST retain their established meaning. New supported states MUST be added
without silently rewriting historical states. Tests MUST verify byte compatibility
for affected historical projections.

### IV. Plan Before Writing; Require Explicit Confirmation
Planning commands MUST be read-only and MUST NOT run project commands or external
services. A write MUST require explicit confirmation of the reviewed plan. Before
the first target-project write, the implementation MUST revalidate the plan and its
preconditions; stale or changed inputs MUST be reported as conflicts.

### V. Make Transactions Reversible and Conflict-Safe
Multi-file changes MUST use the existing snapshot and restore mechanisms. Restore
MUST respect reverse apply order and MUST refuse to overwrite unrelated changes.
Conflicts and partial failures MUST be reported explicitly; the implementation MUST
NOT present an incomplete operation as successful.

### VI. Keep Scope and Authority Bounded
Changes MUST stay within the approved feature scope. They MUST NOT add unrequested
permissions, secrets, external publication, deployment, or access to productive
resources. Secrets MUST NOT be committed or emitted in diagnostics. Any change to
architecture, scope, or access requires the applicable human approval.

### VII. Use Incremental, Verifiable Development
Work MUST proceed through requirements, clarification where material, plan, tasks,
the human Analyze gate, implementation, checks, convergence, and the human Review
gate, proportional to the change. Each meaningful increment MUST have visible
acceptance criteria and focused tests or other explicit evidence. An increment
MUST be reviewable before dependent work proceeds.

## Safety and Compatibility Constraints

- The canonical agent rules, DV concept, generator contract, and approved decisions
  remain authoritative. This constitution supplements them and MUST NOT override
  them. A conflict MUST be reported for human resolution.
- Existing project files MUST NOT be overwritten merely because a generated version
  differs. The established conflict detection and confirmation behavior applies.
- Docker, databases, network services, and external repositories MUST only be used
  within an explicitly approved test or feature scope. A plan or apply operation
  MUST NOT start them unless a separately approved contract explicitly requires it.
- Feature work MUST use a dedicated branch and be delivered for human review through
  a pull request. Pushes, merges, and releases require explicit approval.

## Development Workflow and Gates

- Record feature requirements and measurable acceptance criteria in the selected
  Spec-Driven Development artifacts and update the DV concept only for approved
  architectural decisions.
- Resolve material product or architecture questions with the user; do not convert
  open decisions into implementation assumptions.
- The Analyze gate MUST be reviewed and explicitly approved before implementation.
  The Review gate MUST verify acceptance criteria, test evidence, compatibility,
  and unresolved work before the feature is considered complete.
- Tests MUST cover new behavior and directly affected safety or compatibility
  invariants. Checks not run, blocked environments, and residual risks MUST be
  identified rather than implied to have passed.
- After each meaningful increment, provide a concise status, evidence, remaining
  risks, and the next approval point.

## Governance

This constitution is a project-level guide subordinate to the canonical agent rules,
DV concept, generator contract, and explicit user decisions. Amendments require an
explicitly requested or approved change, a recorded reason, and a semantic version
update: MAJOR for incompatible principle changes, MINOR for new principles or
materially expanded obligations, and PATCH for non-semantic clarification. Feature
plans and reviews MUST check alignment with this constitution and report conflicts;
they MUST NOT silently weaken a principle. Human approval is required at the Analyze
and Review gates and for any architecture, scope, access, or publication decision
reserved by the canonical rules.
